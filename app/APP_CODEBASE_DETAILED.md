# MeshSOS App Codebase: Deep Technical Documentation

## 1. Scope of this document

This document was generated by scanning the Android app module source under:

- `app/src/main/AndroidManifest.xml`
- `app/src/main/java/com/meshsos/**`
- `app/src/main/res/**`
- `app/build.gradle.kts`

The goal is to explain what each main file does and highlight important code blocks.

## 2. High-level architecture

The app follows a layered architecture:

- **Presentation layer**
  - Jetpack Compose screens
  - `MainActivity` tab navigation
  - `MeshViewModel` state exposure and user actions

- **Domain layer**
  - Packet models (`SosPacket`, `AckPacket`)
  - State machine (`MeshStateMachine`) controlling SOS lifecycle
  - Use cases (`SendSosUseCase`, `UploadPacketUseCase`, `RelayPacketUseCase`)
  - Services (`BatteryMonitor`, `AdaptiveScanStrategy`, `DeduplicationService`)

- **Data layer**
  - Transport abstraction (`Transport`) with two implementations:
    - Nearby Connections (WiFi Direct + BLE)
    - BLE GATT fallback
  - Room DB for pending uploads and event logs
  - Retrofit API client + retry interceptor

- **Background runtime**
  - `MeshForegroundService` keeps relay alive and updates notification
  - `BootReceiver` restarts service after reboot

## 3. Main runtime flows

### 3.1 App startup and service boot

1. App process starts with Hilt-enabled `MeshSosApp`.
2. `MainActivity` requests permissions and starts background service through `MeshViewModel.startService()`.
3. `MeshForegroundService` starts transport, subscribes to incoming packets/acks/peer events, and wires callbacks to the state machine.

### 3.2 Sending SOS

1. User long-presses SOS button in `SosScreen`.
2. `MeshViewModel.sendSos()` calls `SendSosUseCase.execute(...)`.
3. Use case collects location, builds `SosPacket`, marks packet as seen in dedup cache, dispatches originator event to state machine, and broadcasts via active transport.
4. UI updates from `meshState`, `peerCount`, and logs.

### 3.3 Receiving and relaying SOS

1. Transport receives packet and emits `incomingPackets`.
2. `MeshForegroundService` forwards packet to `MeshStateMachine.onPacketReceived(...)`.
3. State machine validates dedup/TTL/hop-limit.
4. If internet exists, attempt upload first, else relay immediately.
5. On upload failure, fallback to relay.

### 3.4 Upload and retry behavior

1. `UploadPacketUseCase.upload(...)` hits backend API.
2. On failure, packet is persisted in `pending_packets`.
3. `MeshForegroundService` retry worker periodically calls `retryPending()`.
4. Expired packets are deleted; successful retries are removed from queue.

### 3.5 Logging and debug visibility

- Domain/state/transport events are persisted to `mesh_events`.
- `RelayLogScreen` shows recent events.
- `DebugConsoleScreen` shows all events with filter categories and terminal-like formatting.

## 6. What this app does end-to-end

- Creates and broadcasts emergency SOS packets over local mesh network.
- Relays packets hop-by-hop with TTL and max-hop safety limits.
- Uploads packets to central backend when internet is available.
- Queues failed uploads and retries later.
- Records all mesh events for logs and debugging.
- Runs continuously in foreground service so relay stays alive in background.

## 7. Main technical strengths and caveats

### Strengths

- Good separation of concerns (UI/domain/data/background).
- Transport abstraction with automatic fallback.
- Robust relay safety checks (dedup + TTL + hop limit).
- Strong observability via event logs and debug console.

### Caveats to be aware of

- Nearby and BLE payload schemas must stay compatible with model changes.
- `fallbackToDestructiveMigration()` trades schema safety for simplicity.
- Foreground service and permission behavior can vary across OEM devices.
- Geocoding path in `SendSosUseCase` API 33+ callback style may return empty string if callback resolves after function return.
